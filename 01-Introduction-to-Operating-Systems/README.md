## 💻 مقدمه ای بر سیستم عامل
### 📙 ترجمه کتاب Operating Systems: Three Easy Pieces (OSTEP) 

وقتی یک Program اجرا می‌ شود ، چه اتفاقی می‌ افتد ؟ در ساده‌ ترین حالت ، یک Program در حال اجرا فقط یک کار انجام می‌ دهد آن هم اجرای Instruction ها. Processor در هر ثانیه میلیون‌ ها و امروزه حتی میلیارد ها بار یک Instruction از Memory را Fetch  می‌ کند ، آن را Decode می‌ کند تا مشخص شود چه عملیاتی را باید انجام دهد و سپس آن را Execute می‌ کند. این عملیات می‌ تواند شامل جمع دو عدد ، دسترسی به Memory ، بررسی یک شرط ، پرش به یک Function یا کارهای مشابه باشد. پس از اجرای هر Instruction هم Processor به سراغ دستور بعدی می‌ رود و این روند را آن‌ قدر ادامه می‌ دهد تا سرانجام Program به پایان برسد.

به این ترتیب ، اصول اولیه مدل محاسباتی Von Neumann را توصیف کردیم. ساده به نظر می‌ رسد ، درست است ؟ اما در این درس یاد می‌گیریم که هنگام اجرای یک program، کارهای عجیب و پیچیده دیگری هم در پس‌ زمینه انجام می‌شوند که هدف اصلی آن‌ها آسان‌تر کردن استفاده از سیستم است. در واقع، مجموعه‌ای از software وجود دارد که اجرای program ها را آسان‌ تر می‌ کند. این مجموعه حتی امکان اجرای ظاهری چندین program به‌ صورت هم‌ زمان را فراهم می‌ کند ، به program ها اجازه می‌ دهد memory را با یکدیگر به اشتراک بگذارند ، آن‌ ها را قادر می‌ سازد با device ها تعامل داشته باشند و کارهای جالب دیگری از این دست انجام می‌ دهد. به این مجموعه از software، operating system (OS) می‌گویند زیرا مسئولیت آن این است که سیستم به‌ درستی ، به‌ شکلی کارآمد و با سهولت استفاده کار کند.

روش اصلی OS برای انجام این کار، تکنیکی عمومی به نام virtualization است. در این روش ، OS یک physical  resource مانند processor یا  memory یا disk را می‌ گیرد و آن را به نسخه‌ ای virtual تبدیل می‌ کند که قدرتمند تر و استفاده از آن آسان‌ تر است. به همین دلیل ، گاهی operating system را یک virtual machine نیز می‌ نامیم. البته برای اینکه کاربران بتوانند به OS بگویند چه کاری انجام دهد و از قابلیت‌های virtual machine استفاده کنند ، OS تعدادی interface یا همان API فراهم می‌ کند که می‌ توان آن‌ ها را فراخوانی کرد. این قابلیت‌ ها شامل اجرای یک program ، تخصیص memory یا دسترسی به یک file می‌ شوند. یک OS معمولی در واقع چند صد system call را در اختیار application ها قرار می‌ دهد یا به‌ اصطلاح آن‌ ها را export می‌ کند. از آنجا که OS این call ها را برای اجرای program ها ، دسترسی به memory و device ها و انجام کارهای مرتبط دیگر فراهم می‌ کند ، گاهی می‌ گوییم OS یک standard library در اختیار application ها قرار می‌ دهد.

در نهایت، از آنجا که virtualization امکان اجرای تعداد زیادی program را فراهم می‌ کند ، این program ها می‌ توانند CPU را با یکدیگر به اشتراک بگذارند. همچنین ، بسیاری از program ها می‌ توانند به‌ صورت هم‌ زمان به instruction ها و داده‌ های خود دسترسی داشته باشند و در نتیجه memory را به اشتراک بگذارند. به همین ترتیب ، با دسترسی چندین program به device ها ، منابعی مانند disk نیز به اشتراک گذاشته می‌ شوند. به همین دلیل ، گاهی از OS با عنوان resource manager یاد می‌ شود. هر یک از CPU و memory و disk یک resource از سیستم هستند. بنابراین ، نقش operating system مدیریت این منابع است. چه با هدف کارآمدی ، چه با هدف عدالت در تخصیص منابع و چه با هر هدف دیگری. برای درک بهتر نقش OS ، چند مثال را بررسی می‌ کنیم.

### 2.1 Virtualizing the CPU

برنامه زیر نخستین program ماست و کار چندان پیچیده‌ ای انجام نمی‌ دهد. در واقع ، فقط ()Spin را فراخوانی می‌ کند. function که به‌طور مداوم زمان را بررسی می‌ کند و پس از گذشت یک ثانیه بازمی‌ گردد. سپسstring را که کاربر در command line وارد کرده است چاپ می‌ کند و این کار را تا ابد ادامه می‌ دهد.

```c

#include <stdio.h>
#include <stdlib.h>
#include <sys/time.h>
#include <assert.h>
#include "common.h"

int
main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "usage: cpu <string>\n");
        exit(1);
    }
    char *str = argv[1];
    while (1) {
        Spin(1);
        printf("%s\n", str);
    }
    return 0;
}

```

فرض کنید این file را با نام cpu.c ذخیره می‌ کنیم و تصمیم داریم آن را روی سیستمی با یک processor یا CPU ، که گاهی از این نام هم استفاده می‌کنیم ، compile و اجرا کنیم. نتیجه‌ ای که مشاهده می‌ کنیم به این صورت است :

```
prompt> gcc -o cpu cpu.c -Wall
prompt> ./cpu "A"
A
A
A
A
^C
prompt>
```

اجرای چندان جالبی نیست. سیستم program را شروع می‌ کند و program به‌ طور مداوم زمان را بررسی می‌ کند تا یک ثانیه بگذرد. پس از گذشت یک ثانیه ، string ورودی کاربر را چاپ می‌ کند که در این مثال حرف «A» است و سپس به اجرای خود ادامه می‌ دهد. توجه کنید که این program تا ابد اجرا می‌ شود. تنها راه متوقف کردن آن ، فشردن کلید های ctrl+c است که در سیستم‌ های مبتنی بر UNIX هم program در حال اجرا در foreground را terminate می‌ کند.

حالا همین کار را تکرار می‌ کنیم ، اما این بار چندین instance مختلف از همین program را اجرا می‌ کنیم. شکل زیر نتیجه این مثال کمی پیچیده‌ تر را نشان می‌ دهد :

```
prompt> ./cpu A & ; ./cpu B & ; ./cpu C & ; ./cpu D &

[4] 7356
A
B
D
C
A

C
A
C
B

```

خب ، حالا موضوع جالب‌ تر شد. با اینکه فقط یک processor داریم ، به نظر می‌ رسد هر چهار program به‌ صورت هم‌ زمان در حال اجرا هستند ، این اتفاق چگونه رخ می‌ دهد ؟

> توجه : با استفاده از نماد & ، چهار process را به صورت هم‌ زمان اجرا کردیم. این کار در shell از نوع tcsh ، یک job را در background اجرا می‌ کند. یعنی کاربر می‌ تواند بلافاصله دستور بعدی را وارد کند که در این مثال ، اجرای یک program دیگر است. semi-colon بین دستورها در tcsh امکان اجرای چند program را به‌صورت هم‌ زمان فراهم می‌ کند. اگر از shell دیگری مثلاً bash ، استفاده می‌ کنید این فرایند کمی متفاوت خواهد بود.

مشخص می‌ شود که operating system با کمک hardware مسئول ایجاد این توهم است. توهمی مبنی بر اینکه سیستم تعداد بسیار زیادی CPU مجازی (virtual CPU) دارد. تبدیل یک CPU (یا مجموعه کوچکی از آن‌ ها) به تعداد به‌ ظاهر بی‌ نهایتی CPU ، به‌ گونه‌ ای که امکان اجرای ظاهراً هم‌ زمان تعداد زیادی program فراهم شود ، همان چیزی است که آن را virtualizing the CPU می‌ نامیم. این موضوع ، محور اصلی نخستین بخش از کتاب است.

البته برای اجرای program ها ، متوقف کردن آن‌ ها و به‌ طور کلی مشخص کردن اینکه OS کدام program ها را اجرا کند ، باید interface هایی یا API هایی وجود داشته باشند تا بتوانیم خواسته‌ های خود را از طریق آن‌ ها به OS اعلام کنیم. در سراسر این کتاب درباره این API ها صحبت خواهیم کرد. در واقع ، این API ها اصلی‌ ترین راه تعامل بیشتر کاربران با operating system ها هستند. 

شاید متوجه شده باشید که قابلیت اجرای چند program به‌ صورت هم‌ زمان ، پرسش‌ های جدیدی را مطرح می‌کند. برای مثال ، اگر دو program بخواهند در یک زمان مشخص اجرا شوند ، کدام‌ یک باید اجرا شود ؟ پاسخ این پرسش را یک policy در OS تعیین می‌ کند. policy ها در بخش‌ های مختلف OS برای پاسخ به چنین پرسش‌ هایی به کار می‌ روند. هنگام یادگیری mechanism های پایه‌ ای که operating system ها برای پیاده‌ سازی قابلیت‌ هایی مانند اجرای هم‌ زمان چند program به کار می‌ گیرند ، این policy ها را نیز بررسی خواهیم کرد. به همین دلیل است که OS نقش یک resource manager را بر عهده دارد.

### 2.2 Virtualizing Memory

حالا به memory می‌ پردازیم. مدلی که ماشین‌ های مدرن از physical memory ارائه می‌ دهند ، بسیار ساده است. Memory فقط آرایه‌ ای از byte هاست. برای خواندن از memory ، باید یک address مشخص کنیم تا بتوانیم به داده ذخیره‌ شده در آن دسترسی پیدا کنیم. برای نوشتن (write) یا به‌ روزرسانی (update) داده در memory نیز باید علاوه بر address ، داده‌ ای را که می‌ خواهیم در آن address بنویسیم ، مشخص کنیم.

در طول اجرای یک program ، دسترسی به memory به‌ طور مداوم اتفاق می‌ افتد. هر program تمام data structure های خود را در memory نگه می‌ دارد و از طریق instruction های مختلف ، مانند load و store ، یا دیگر instruction هایی که برای انجام وظایفشان به memory دسترسی دارند ، از آن‌ ها استفاده می‌ کند. فراموش نکنید که خودِ هر instruction از program نیز در memory قرار دارد. بنابراین هر بار که یک instruction را fetch می‌ کنیم دسترسی دیگری به memory صورت می‌ گیرد.

بیایید program زیر را بررسی کنیم که با فراخوانی ()malloc مقداری memory تخصیص می‌ دهد :

```c
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
#include "common.h"

int
main(int argc, char *argv[])
{
    int *p = malloc(sizeof(int));             // a1
    assert(p != NULL);
    printf("(%d) address of p: %08x\n",
           getpid(), (unsigned) p);           // a2
    *p = 0;                                   // a3
    while (1) {
        Spin(1);
        *p = *p + 1;
        printf("(%d) p: %d\n", getpid(), *p); // a4
    }
    return 0;
}
```

خروجی این program را در این‌ جا می‌ بینید :

```
prompt> ./mem
(2134) memory address of p: 00200000
(2134) p: 1
(2134) p: 2
(2134) p: 3
(2134) p: 4
(2134) p: 5
^C
```

این program چند کار انجام می‌ دهد. ابتدا مقداری memory تخصیص می‌ دهد (خط a1) سپس address آن memory را چاپ می‌کند (a2) و بعد عدد صفر را در نخستین slot از memory تازه‌ تخصیص‌ یافته قرار می‌ دهد (a3). در نهایت ، وارد یک حلقه می‌ شود ، یک ثانیه تأخیر می‌ کند و مقدار ذخیره‌ شده در address را که p نگه داشته است، یک واحد افزایش می‌ دهد.

با هر دستور print ، مقداری به نام process identifier (یا همان PID) مربوط به program در حال اجرا نیز چاپ می‌ شود. این PID برای هر process در حال اجرا یکتاست.

باز هم ، نتیجه اولیه چندان جالب نیست. memory تازه‌ تخصیص‌ یافته در address 00200000 قرار دارد. با اجرای program ، مقدار به‌ آرامی به‌ روزرسانی می‌ شود و نتیجه چاپ می‌ گردد. حالا چند instance دیگر از همین program را اجرا می‌ کنیم تا ببینیم چه اتفاقی می‌ افتد :

```
prompt> ./mem &; ./mem &
[1] 24113
[2] 24114
(24113) memory address of p: 00200000
(24114) memory address of p: 00200000
(24113) p: 1
(24114) p: 1
(24114) p: 2
(24113) p: 2
(24113) p: 3
(24114) p: 3
(24113) p: 4
(24114) p: 4
...
```

از این مثال می‌ بینیم که هر program در حال اجرا ، memory را در همان address ، یعنی 00200000 ، تخصیص داده است. با این حال، به نظر می‌ رسد هرکدام مقدار موجود در این address را مستقل از دیگری به‌ روزرسانی می‌ کند. به عبارت دیگر، هر program در حال اجرا memory خصوصی خودش را دارد ، نه اینکه همان physical memory را با سایر program های در حال اجرا به اشتراک بگذارد.

در واقع ، دقیقاً همین اتفاق در حال رخ دادن است زیرا OS مشغول virtualizing memory است. هر process به virtual address space خصوصی خودش دسترسی دارد (که گاهی فقط address space نامیده می‌ شود) و OS به‌ نوعی آن را روی physical memory ماشین map می‌ کند. یک memory reference درون یک program در حال اجرا ، بر address space سایر process ها یا حتی خود OS تأثیری نمی‌ گذارد. از دید program در حال اجرا ، گویی تمام physical memory فقط به خودش تعلق دارد. اما واقعیت این است که physical memory یک resource مشترک است که operating system آن را مدیریت می‌ کند. اینکه دقیقاً چگونه تمام این کارها انجام می‌ شود ، موضوع بخش اول این کتاب ، یعنی virtualization است.

### 2.3 Concurrency

یکی دیگر از موضوعات اصلی این کتاب concurrency است. از این اصطلاح برای اشاره به مجموعه‌ ای از مسائل استفاده می‌ کنیم که هنگام انجام چند کار به‌ صورت هم‌ زمان concurrently درون یک program به وجود می‌آیند و باید حل شوند. مسائل concurrency ابتدا در خود operating system پدیدار شدند. همان‌ طور که در مثال‌ های قبلی مربوط به virtualization دیدید ، OS چندین کار را به صورت هم‌ زمان مدیریت می‌کند ابتدا یک process را اجرا می‌ کند سپس به سراغ process دیگری می‌ رود و همین روند را ادامه می‌ دهد که مشخص می‌ شود که انجام این کار به مسائل عمیق و جالبی منجر می‌ شود. متأسفانه ، مسائل concurrency دیگر فقط به خود OS محدود نیستند. در واقع ، program های مدرن multi-threaded نیز با همین مسائل رو به‌ رو می‌ شوند. بیایید این موضوع را با مثالی از یک program (multi-threaded) نشان دهیم :

```c
#include <stdio.h>
#include <stdlib.h>
#include "common.h"

volatile int counter = 0;
int loops;

void *worker(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        counter++;
    }
    return NULL;
}

int
main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "usage: threads <value>\n");
        exit(1);
    }
    loops = atoi(argv[1]);
    pthread_t p1, p2;
    printf("Initial value : %d\n", counter);

    Pthread_create(&p1, NULL, worker, NULL);
    Pthread_create(&p2, NULL, worker, NULL);
    Pthread_join(p1, NULL);
    Pthread_join(p2, NULL);
    printf("Final value   : %d\n", counter);
    return 0;
}
```

ممکن است فعلاً این مثال را به‌ طور کامل درک نکنید. در فصل‌ های بعدی ، در بخش مربوط به concurrency ، مطالب بسیار بیشتری درباره آن یاد خواهیم گرفت اما ایده اصلی ساده است. program اصلی با استفاده از()Pthread_create دو thread ایجاد می‌ کند. می‌ توانید یک thread را مانند function در نظر بگیرید که در همان memory space سایر function ها اجرا می‌ شود. با این تفاوت که ممکن است بیش از یک thread به‌ صورت هم‌ زمان فعال باشد. در این مثال ، هر thread اجرای خود را از روتینی به نام()worker آغاز می‌ کند که در آن ، یک counter درون حلقه‌ ای به تعداد loops بار افزایش می‌ یابد. 

در ادامه ، خروجی اجرای این program را با مقداردهی متغیر loops به عدد 1000 مشاهده می‌ کنید. مقدار loops مشخص می‌کند که هر یک از دو worker چند بار counter مشترک را در یک حلقه افزایش دهد. اگر program را با مقدار loops برابر 1000 اجرا کنیم ، انتظار دارید مقدار نهایی counter چه باشد ؟

```
prompt> gcc -o thread thread.c -Wall -pthread
prompt> ./thread 1000
Initial value : 0
Final value   : 2000
```

همان‌ طور که احتمالاً حدس زده‌ اید ، وقتی هر دو thread به پایان می‌ رسند ، مقدار نهایی counter برابر 2000 است زیرا هر thread مقدار counter را 1000 بار افزایش داده است. در واقع ، اگر مقدار ورودی loops برابر N باشد ، انتظار داریم خروجی نهایی program برابر 2N باشد. اما مشخص می‌ شود که ماجرا به این سادگی نیست. بیایید همین program را با مقادیر بزرگ‌ تری برای loops اجرا کنیم و ببینیم چه اتفاقی می‌ افتد :

```
prompt> ./thread 100000
Initial value : 0
Final value   : 143012      // huh??
prompt> ./thread 100000
Initial value : 0
Final value   : 137298      // what the??
```

در این اجرا ، وقتی مقدار ورودی را 100,000 قرار دادیم ، به‌ جای مقدار نهایی 200,000 ، ابتدا به عدد 143,012 رسیدیم. سپس وقتی program را برای بار دوم اجرا کردیم، نه‌ تنها دوباره نتیجه اشتباهی گرفتیم بلکه این بار مقدار متفاوتی نسبت به اجرای قبلی به دست آمد. در واقع ، اگر program را بارها و بارها با مقادیر بزرگ loops اجرا کنید، ممکن است گاهی حتی پاسخ درست را هم دریافت کنید. پس چرا چنین اتفاقی می‌ افتد ؟

مشخص می‌ شود که دلیل این نتایج عجیب و غیرمعمول ، به نحوه اجرای instruction ها مربوط است یعنی اینکه آن‌ ها یکی‌ یکی اجرا می‌ شوند. متأسفانه ، بخش کلیدی program بالا ، یعنی جایی که counter مشترک افزایش می‌ یابد ، به سه instruction نیاز دارد :

- یک instruction برای load کردن مقدار counter از memory به یک register.
- یک instruction برای افزایش مقدار آن.
- یک instruction برای store کردن مقدار جدید در memory.

از آنجا که این سه instruction به‌ صورت atomic اجرا نمی‌ شوند یعنی همگی به‌ عنوان یک عملیات واحد و یک‌ جا انجام نمی‌ گیرند ، ممکن است اتفاقات عجیبی رخ دهد. این دقیقاً همان مسئله concurrency است که در بخش دوم کتاب ، با جزئیات فراوان به آن خواهیم پرداخت.

### 2.4 Persistence

چهارمین موضوع اصلی این درس persistence است. در system memory ، داده‌ ها به‌ راحتی از بین می‌روند زیرا  device هایی مانند DRAM ، مقادیر را به‌ صورت volatile ذخیره می‌ کنند. وقتی برق قطع شود یا سیستم crash کند ، تمام داده‌ های موجود در memory از بین می‌ روند. بنابراین ، به hardware و software هایی نیاز داریم که بتوانند داده‌ ها را به‌ صورت persistent ذخیره کنند. چنین ذخیره‌ سازی‌ای برای هر سیستمی حیاتی است زیرا کاربران برای داده‌ های خود اهمیت زیادی قائل‌اند. hardware مورد نیاز، به‌ شکل نوعی device از جنس input/output یا I/O است. در سیستم‌ های مدرن ، hard drive مخزن رایج اطلاعات بلند مدت است ، هرچند **solid-state drive (SSD)**ها نیز در این زمینه در حال پیشرفت هستند. software که در operating system معمولاً مسئول مدیریت disk است ، file system نام دارد. بنابراین ، مسئولیت ذخیره‌ سازی قابل‌ اعتماد و کارآمد هر file که کاربر ایجاد می‌ کند ، روی disk های سیستم بر عهده آن است.

برخلاف abstraction هایی که OS برای CPU و memory فراهم می‌ کند ، OS برای هر application یک disk خصوصی و virtualized ایجاد نمی‌ کند. در عوض ، فرض بر این است که بیشتر کاربران می‌ خواهند اطلاعات موجود در file هایشان را با یکدیگر به اشتراک بگذارند. برای مثال ، هنگام نوشتن یک برنامه C ، ممکن است ابتدا از یک editor مثلاً Emacs ، برای ایجاد و ویرایش file زبان C استفاده کنید :

```
emacs -nw main.c
```

وقتی کارتان تمام شد ، ممکن است از compiler برای تبدیل source code به یک executable استفاده کنید :

```
gcc -o main main.c
```

پس از اتمام این مرحله ، می‌ توانید executable جدید را اجرا کنید :

```
./main
```

به این ترتیب ، می‌بینید که چگونه file ها میان process های مختلف به اشتراک گذاشته می‌ شوند. Emacs ابتدا file ایجاد می‌ کند که به‌ عنوان ورودی compiler استفاده می‌ شود. سپس compiler از آن file ورودی برای ایجاد یک file اجرایی جدید استفاده می‌ کند. در نهایت ، executable جدید اجرا می‌ شود و به این ترتیب یک program جدید متولد می‌ شود.

برای درک بهتر این موضوع ، بیایید نگاهی به مقداری کد بیندازیم. کد زیر file به نام tmp/file/ ایجاد می‌ کند که حاوی string با مقدار hello world است :

```c
#include <stdio.h>
#include <unistd.h>
#include <assert.h>
#include <fcntl.h>
#include <sys/types.h>

int
main(int argc, char *argv[])
{
    int fd = open("/tmp/file", O_WRONLY | O_CREAT | O_TRUNC, S_IRWXU);
    assert(fd > -1);
    int rc = write(fd, "hello world\n", 13);
    assert(rc == 13);
    close(fd);
    return 0;
}
```

برای انجام این کار، program سه فراخوانی به operating system انجام می‌ دهد :

- فراخوانی اول یعنی()open فایل را باز می‌ کند و در صورت نیاز آن را ایجاد می‌کند.
- فراخوانی دوم یعنی()write مقداری داده در file می‌ نویسد.
- فراخوانی سوم، یعنی()close صرفاً file را می‌ بندد و به این ترتیب نشان می‌ دهد که program دیگر داده‌ ای در آن نخواهد نوشت.

این system call ها به بخشی از operating system به نام file system هدایت می‌ شوند. file system سپس درخواست‌ ها را پردازش می‌ کند و نوعی error code به کاربر بازمی‌ گرداند.

ممکن است کنجکاو باشید که OS برای نوشتن واقعی داده روی disk چه کارهایی انجام می‌ دهد. این موضوع را برایتان توضیح می‌ دهیم، اما باید قول بدهید ابتدا چشمانتان را ببندید ، چون فرایند چندان خوشایندی نیست. file system باید کارهای نسبتاً زیادی انجام دهد. ابتدا باید مشخص کند که داده جدید در کجای disk قرار بگیرد و سپس آن را در ساختارهای مختلفی که file system نگهداری می‌ کند، ثبت و پیگیری کند. انجام این کار مستلزم صدور I/O request هایی به storage device زیرین است ، چه برای خواندن ساختارهای موجود و چه برای به‌ روزرسانی آن‌ ها. هر کسی که device driver نوشته باشد ، می‌داند که وادار کردن یک device به انجام کاری از طرف شما ، فرایندی پیچیده و پر از جزئیات است. این کار به دانش عمیقی درباره low-level device interface و semantics دقیق آن نیاز دارد. خوشبختانه ، OS از طریق system call های خود ، راهی استاندارد و ساده برای دسترسی به device ها فراهم می‌ کند. به همین دلیل ، گاهی OS را نوعی standard library در نظر می‌ گیریم.

البته جزئیات بسیار بیشتری درباره نحوه دسترسی به device ها و چگونگی مدیریت persistent داده‌ ها روی آن‌ ها توسط file system ها وجود دارد. به دلایل مربوط به performance ، بیشتر file system ها ابتدا نوشتن‌ ها را برای مدتی به تأخیر می‌ اندازند ، به این امید که بتوانند آن‌ ها را در گروه‌ های بزرگ‌ تری به‌ صورت batch انجام دهند. برای مدیریت مشکل crash شدن سیستم در حین نوشتن ، بیشتر file system ها نوعی write protocol پیچیده ، مانند journaling یا copy-on-write ، در خود دارند. آن‌ ها نوشتن‌ ها روی disk را با دقت مرتب می‌ کنند تا اگر در میانه یک توالی نوشتن ، خرابی رخ داد ، سیستم بتواند پس از آن به وضعیتی معقول بازیابی شود. برای کارآمد کردن عملیات رایج مختلف ، file system ها از data structure ها و access method های متنوعی استفاده می‌ کنند ، از list های ساده گرفته تا b-tree های پیچیده. اگر هنوز این مفاهیم برایتان معنایی ندارند، عالی است. در بخش سوم این کتاب ، درباره persistence ، مطالب بسیار بیشتری درباره تمام این موارد خواهیم آموخت. ابتدا درباره device ها و I/O به‌ طور کلی بحث می‌ کنیم و سپس با جزئیات فراوان به سراغ disk ها ، RAID ها و file  system ها می‌ رویم.

### 2.5 Design Goals

حالا تا حدی می‌ دانید که یک OS واقعاً چه کارهایی انجام می‌ دهد: physical resource هایی مانند CPU یا memory یا disk را می‌ گیرد و آن‌ ها را virtualize می‌ کند. با مسائل دشوار و ظریف مربوط به concurrency دست‌ و پنجه نرم می‌ کند و  file ها را به‌ صورت persistent ذخیره می‌ کند تا در بلند مدت ایمن باقی بمانند. با توجه به اینکه قصد داریم چنین سیستمی بسازیم ، باید اهدافی را در نظر داشته باشیم که به متمرکز شدن طراحی و پیاده‌ سازی کمک کنند و در صورت نیاز، امکان برقراری trade-off را فراهم آورند. یافتن مجموعه مناسبی از trade-off ها ، کلید ساخت سیستم‌ هاست.

یکی از اساسی‌ ترین اهداف ، ساخت مجموعه‌ ای از abstraction هاست تا استفاده از سیستم راحت‌ تر و آسان‌ تر شود. abstraction ها در تمام کارهایی که در computer science انجام می‌ دهیم، نقش اساسی دارند. abstraction به ما امکان می‌ دهد یک program بزرگ را با تقسیم آن به بخش‌ های کوچک و قابل‌ فهم بنویسیم. برای مثال ، می‌ توانیم یک program را با زبان سطح‌ بالایی مانند C بنویسیم ، بدون اینکه لازم باشد به assembly فکر کنیم. می‌ توانیم کد را به assembly بنویسیم ، بدون اینکه نگران logic gate ها باشیم. همچنین می‌توانیم یک processor را با استفاده از gate ها بسازیم ، بدون اینکه لازم باشد زیاد به transistor ها فکر کنیم. abstraction آن‌ قدر بنیادی است که گاهی اهمیت آن را فراموش می‌ کنیم اما ما در این کتاب چنین نخواهیم کرد. بنابراین ، در هر بخش درباره برخی از abstraction های مهمی که در طول زمان شکل گرفته‌ اند بحث می‌ کنیم تا چارچوبی برای فکر کردن درباره اجزای OS در اختیارتان قرار دهیم.

یکی دیگر از اهداف طراحی و پیاده‌ سازی یک operating system ، دستیابی به high performance است. به عبارت دیگر، هدف ما به حداقل رساندن overhead های مربوط به OS است. virtualization و آسان‌ تر کردن استفاده از سیستم ، ارزش زیادی دارند اما نه به هر قیمتی. بنابراین باید تلاش کنیم virtualization و سایر قابلیت‌ های OS را بدون ایجاد overhead های بیش از حد فراهم کنیم. این overhead ها به شکل‌ های مختلفی ظاهر می‌ شوند: زمان اضافی ناشی از اجرای instruction های بیشتر و فضای اضافی در memory یا روی disk. ما به دنبال راه‌ حل‌ هایی خواهیم بود که در صورت امکان ، یکی از این دو یا هر دوی آن‌ ها را کاهش دهند. با این حال ، دستیابی به کمال همیشه ممکن نیست موضوعی که یاد می‌ گیریم آن را درک کنیم و در موقعیت‌ های مناسب بپذیریم.

هدف دیگر، فراهم کردن protection میان application ها و همچنین میان OS و application هاست. از آنجا که می‌ خواهیم تعداد زیادی program به‌ صورت هم‌ زمان اجرا شوند ، باید مطمئن شویم که رفتار مخرب یا حتی تصادفی یکی از آن‌ ها به سایر program ها آسیب نمی‌ زند. قطعاً نمی‌ خواهیم یک application بتواند به خود OS آسیب برساند زیرا چنین اتفاقی بر تمام program های در حال اجرا روی سیستم تأثیر می‌ گذارد. protection در قلب یکی از اصول اساسی زیربنای یک operating system ، یعنی isolation قرار دارد. جداسازی process ها از یکدیگر، کلید protection است و در نتیجه ، زیربنای بخش بزرگی از کارهایی به شمار می‌ رود که یک OS باید انجام دهد.

همچنین ، operating system باید بدون وقفه به کار خود ادامه دهد. اگر OS fail شود ، تمام application های در حال اجرا روی سیستم نیز fail خواهند شد. به‌ دلیل این وابستگی ، operating system ها اغلب تلاش می‌ کنند سطح بالایی از reliability را فراهم کنند. با پیچیده‌ تر شدن روزافزون operating system ها ، که گاهی میلیون‌ ها خط کد دارند ، ساختن یک operating system قابل‌اعتماد به چالشی بزرگ تبدیل شده است. در واقع ، بخش زیادی از پژوهش‌ های جاری در این حوزه دقیقاً بر همین مسئله متمرکز است.

اهداف منطقی دیگری نیز وجود دارند. برای مثال ، energy-efficiency اهمیت دارد. security که در واقع گسترشی از protection است ، برای مقابله با application های مخرب حیاتی است. به‌ ویژه در دنیای امروزی که به‌ شدت شبکه‌ ای شده است ، mobility نیز اهمیت فزاینده‌ ای دارد زیرا OS ها روی device هایی اجرا می‌ شوند که هر روز کوچک‌ تر می‌ شوند. بسته به نحوه استفاده از سیستم ، OS اهداف متفاوتی خواهد داشت و در نتیجه ، احتمالاً دست‌ کم تا حدی متفاوت پیاده‌ سازی می‌ شود. با این حال ، همان‌ طور که خواهیم دید ، بسیاری از اصولی که درباره ساخت operating system ها مطرح می‌ کنیم ، در طیف گسترده‌ای از device ها کاربرد دارند.

### 2.6 Some History

پیش از پایان دادن به این مقدمه ، تاریخچه کوتاهی از چگونگی توسعه operating system ها ارائه می‌ کنیم. مانند هر سیستم دیگری که انسان‌ ها ساخته‌ اند ، ایده‌ های خوب به‌ مرور زمان در operating system ها انباشته شده‌اند همان‌ طور که مهندسان به‌ تدریج آموخته‌ اند چه چیزهایی در طراحی آن‌ ها اهمیت دارند. در این‌ جا چند تحول عمده را بررسی می‌ کنیم. برای مطالعه بحثی غنی‌تر، می‌ توانید به تاریخچه عالی Brinch Hansen درباره operating system ها مراجعه کنید.

#### Early Operating Systems: Just Libraries

در ابتدا، operating system کار چندانی انجام نمی‌ داد. در اصل ، فقط مجموعه‌ ای از library های حاوی function های پرکاربرد بود. برای مثال ، به‌ جای اینکه هر programmer مجبور باشد کد low-level مربوط به مدیریت I/O را خودش بنویسد ، OS چنین API هایی را فراهم می‌ کرد و در نتیجه کار را برای developer آسان‌ تر می‌ ساخت. معمولاً در آن سیستم‌ های قدیمی mainframe ، در هر زمان فقط یک program اجرا می‌ شد که یک operator انسانی آن را کنترل می‌ کرد. بسیاری از کارهایی که تصور می‌ کنید یک OS مدرن انجام می‌ دهد ، مانند تصمیم‌ گیری درباره ترتیب اجرای job ها ، در آن زمان بر عهده همین operator بود. اگر developer باهوشی بودید ، با این operator رفتار خوبی می‌ کردید تا شاید job شما را به ابتدای صف منتقل کند. این شیوه محاسباتی batch processing نامیده می‌ شد زیرا تعدادی job آماده می‌ شدند و سپس operator آن‌ ها را به‌ صورت یک batch اجرا می‌ کرد. در آن زمان ، از computer ها به‌ صورت interactive استفاده نمی‌ شد. دلیلش هزینه بسیار بالای آن‌ ها بود. نشستن یک کاربر پشت computer و استفاده مستقیم از آن ، آن‌ قدر پرهزینه بود که عملاً صرفه اقتصادی نداشت زیرا بیشتر اوقات computer در حالت idle باقی می‌ ماند و برای آن مرکز، ساعتی صدها هزار دلار هزینه ایجاد می‌ کرد.

#### Beyond Libraries: Protection

با گذر از یک library ساده از سرویس‌ های پرکاربرد به سمت سیستم‌ هایی پیشرفته‌ تر، operating system ها نقش محوری‌ تری در مدیریت ماشین‌ ها بر عهده گرفتند. یکی از جنبه‌ های مهم این تحول ، درک این موضوع بود که کدی که از طرف OS اجرا می‌ شود ، ماهیتی ویژه دارد. این کد کنترل device ها را در اختیار دارد و بنابراین باید با آن متفاوت از کد های معمولی application ها برخورد شود. چرا؟

به‌جای اینکه روتین‌ های OS را به‌ صورت یک library عرضه کنند که دسترسی به آن‌ ها فقط به یک procedure call نیاز داشت ، ایده این بود که یک جفت instruction ویژه hardware و hardware state اضافه شود تا انتقال کنترل به درون OS به فرایندی رسمی‌ تر و کنترل‌ شده‌ تر تبدیل شود. 

تفاوت کلیدی میان system call و procedure call این است که system call کنترل را به درون OS منتقل می‌ کند و هم‌ زمان hardware privilege level را افزایش می‌ دهد. application های کاربر در حالتی اجرا می‌ شوند که user mode نام دارد. در این حالت ، hardware فعالیت‌ هایی را که applicationها می‌ توانند انجام دهند ، محدود می‌ کند. برای مثال ، application که در user mode اجرا می‌ شود ، معمولاً نمی‌ تواند یک I/O request به disk آغاز کند ، به هر physical memory page دسترسی پیدا کند یا یک packet روی network بفرستد.

وقتی یک system call آغاز می‌ شود ، معمولاً hardware از طریق یک instruction ویژه به نام trap ، کنترل را به trap handler منتقل می‌ کند که OS از پیش آن را تنظیم کرده است. هم‌ زمان، privilege level نیز به kernel mode ارتقا می‌یابد. در kernel mode هم OS دسترسی کامل به hardware سیستم دارد و در نتیجه می‌ تواند کارهایی مانند آغاز یک I/O request یا اختصاص memory بیشتر به یک program را انجام دهد. وقتی OS رسیدگی به درخواست را به پایان می‌ رساند ، کنترل را از طریق instruction ویژه‌ ای به نام return-from-trap به کاربر بازمی‌ گرداند. در این مرحله ، سیستم به user mode برمی‌ گردد و کنترل نیز به همان نقطه‌ ای بازمی‌ گردد که application در آن متوقف شده بود.

#### The Era of Multiprogramming

جایی که operating system ها واقعاً به اوج رسیدند، دوره پس از mainframe بود یعنی عصر minicomputer ها. ماشین‌ های کلاسیکی مانند خانواده PDP از شرکت Digital Equipment ، قیمت computer ها را به‌ شدت کاهش دادند. در نتیجه ، به‌ جای اینکه هر سازمان بزرگ فقط یک mainframe داشته باشد، حالا گروه کوچک‌ تری از افراد درون یک سازمان نیز احتمالاً می‌ توانستند computer مخصوص خودشان را داشته باشند. جای تعجب نیست که یکی از پیامد های عمده این کاهش هزینه ، افزایش فعالیت developer ها بود. افراد باهوش بیشتری به computer ها دسترسی پیدا کردند و در نتیجه ، سیستم‌ های computer را به انجام کارهای جالب‌ تر و خلاقانه‌ تری واداشتند.

به‌ طور خاص ، multiprogramming به‌ دلیل تمایل به استفاده بهتر از resource های ماشین رواج پیدا کرد. به‌ جای اینکه در هر زمان فقط یک job اجرا شود ، OS تعدادی job را در memory بارگذاری می‌ کرد و به‌ سرعت میان آن‌ ها switch می‌ کرد به این ترتیب ، CPU utilization بهبود می‌ یافت. این switch کردن به‌ ویژه اهمیت داشت زیرا I/O device ها کند بودند. منتظر ماندن یک program روی CPU تا زمانی که I/O آن سرویس‌ دهی شود ، به معنای هدر رفتن زمان CPU بود. پس چرا به job دیگری switch نکنیم و آن را برای مدتی اجرا نکنیم ؟

تمایل به پشتیبانی از multiprogramming و overlap در حضور I/O و interrupt ها ، توسعه مفهومی operating system ها را در مسیرهای مختلفی به نوآوری واداشت. مسائلی مانند memory protection اهمیت پیدا کردند. نمی‌ خواهیم یک program بتواند به memory مربوط به program دیگری دسترسی داشته باشد. درک چگونگی مقابله با مسائل concurrency که multiprogramming به وجود آورد نیز حیاتی بود. همچنین ، اطمینان از اینکه OS با وجود interrupt ها به‌ درستی رفتار می‌ کند ، چالشی بزرگ به شمار می‌ رفت. این مسائل و موضوعات مرتبط با آن‌ ها را در ادامه کتاب بررسی خواهیم کرد.

یکی از پیشرفت‌ های عملی بزرگ آن دوره ، معرفی operating system ای به نام UNIX بود. سیستمی که عمدتاً به لطف Ken Thompson و Dennis Ritchie در Bell Labs ، همان شرکت تولید کننده تلفن ، توسعه یافت. UNIX ایده‌ های خوب بسیاری را از operating system های مختلف گرفت ، اما آن‌ ها را ساده‌ تر و استفاده از آن‌ ها را آسان‌ تر کرد. این تیم نوارهایی حاوی source code سیستم UNIX را برای افرادی در سراسر جهان می‌ فرستاد. بسیاری از دریافت‌ کنندگان این نوارها به پروژه پیوستند و خودشان قابلیت‌ های جدیدی به سیستم اضافه کردند.

#### The Modern Era

پس از minicomputer ها ، نوع جدیدی از ماشین‌ ها پدیدار شد که ارزان‌ تر، سریع‌ تر و برای عموم مردم در دسترس‌ تر بود به نام personal computer یا همان PC که امروزه می‌ شناسیم. با ظهور ماشین‌ های اولیه Apple مانند Apple II و IBM PC، این نسل جدید از ماشین‌ ها به‌ سرعت به نیروی غالب در دنیای محاسبات تبدیل شد زیرا هزینه پایین آن‌ ها امکان داشتن یک ماشین برای هر میز کار را فراهم می‌ کرد ، به‌ جای اینکه هر گروه کاری مجبور باشد از یک minicomputer مشترک استفاده کند. 

متأسفانه ، از نظر operating system ها ، ظهور PC در ابتدا گامی بزرگ به عقب بود زیرا سیستم‌ های اولیه ، درس‌ هایی را که در دوران minicomputer آموخته شده بود ، فراموش کرده بودند یا اصلاً از آن‌ ها اطلاعی نداشتند. برای مثال ، operating system های اولیه‌ ای مانند DOS مخفف Disk Operating System محصول Microsoft ، اهمیت چندانی برای memory protection قائل نبودند. بنابراین ، یک application مخرب می‌ توانست در تمام memory دست‌ کاری کند. نسل‌ های اولیه Mac OS ، یعنی نسخه 9 و نسخه‌ های پیش از آن ، رویکردی cooperative برای job scheduling داشتند. در نتیجه، اگر یک thread به‌ طور اتفاقی درون یک infinite loop گرفتار می‌ شد، می‌ توانست کنترل کل سیستم را در اختیار بگیرد و سیستم را مجبور به reboot کند. فهرست ویژگی‌ های مهم OS که در این نسل از سیستم‌ ها وجود نداشت ، طولانی است آن‌ قدر طولانی که نمی‌توانیم تمام آن را در این‌جا بررسی کنیم.

خوشبختانه ، پس از چند سال دشواری ، ویژگی‌ های قدیمی operating system های minicomputer راه خود را به desktop ها پیدا کردند. برای مثال ، Mac OS X در هسته خود UNIX دارد و تمام ویژگی‌ هایی را ارائه می‌ کند که از چنین سیستم بالغی انتظار می‌ رود. Windows نیز به‌ طور مشابه بسیاری از ایده‌ های ارزشمند تاریخ computing را پذیرفته است به‌ ویژه از زمان Windows NT که جهشی بزرگ در فناوری OS شرکت Microsoft به شمار می‌ رفت. حتی تلفن‌ های همراه امروزی نیز operating system هایی مانند Linux را اجرا می‌ کنند که بسیار بیشتر به چیزی شباهت دارند که یک minicomputer در دهه 1970 اجرا می‌ کرد تا آنچه یک PC در دهه 1980 اجرا می‌ کرد. 

خوشحال‌کننده است که می‌بینیم ایده‌ های خوبی که در دوران اوج توسعه OS پدید آمدند ، راه خود را به دنیای مدرن پیدا کرده‌ اند. حتی بهتر اینکه این ایده‌ ها همچنان در حال توسعه‌ اند، قابلیت‌ های بیشتری فراهم می‌ کنند و سیستم‌ های مدرن را برای کاربران و application ها بهتر از گذشته می‌ سازند.


#### ASIDE: THE IMPORTANCE OF UNIX

بیان اهمیت UNIX در تاریخ operating system ها دشوار است زیرا هر چه درباره آن بگوییم ، باز هم حق مطلب ادا نمی‌ شود. UNIX که تحت تأثیر سیستم‌ های پیشین، به‌ ویژه سیستم مشهور Multics از MIT شکل گرفت ، ایده‌ های عالی بسیاری را گرد هم آورد و سیستمی ساخت که هم ساده بود و هم قدرتمند. اصل یکپارچه‌ کننده در زیربنای UNIX اولیه در Bell Labs این بود که ساختن program های کوچک و قدرتمندی که بتوان آن‌ ها را به یکدیگر متصل کرد تا workflow های بزرگ‌تری ایجاد شوند.  Shell ، جایی که دستورها را در آن تایپ می‌کنید ، primitive هایی مانند pipe ها را فراهم کرد تا چنین meta-level programming امکان‌پذیر شود. به این ترتیب ، به‌ هم‌ زنجیر کردن program ها برای انجام کاری بزرگ‌ تر آسان شد. برای مثال، اگر بخواهید خط‌ هایی از یک text file را پیدا کنید که کلمه foo در آن‌ ها وجود دارد و سپس تعداد این خط‌ ها را بشمارید ، می‌ توانید دستور زیر را وارد کنید :

```grep foo file.txt|wc -l```

به این ترتیب ، از program های grep و wc برای انجام کار مورد نظرتان استفاده می‌ کنید.

محیط UNIX هم برای programmer ها و هم برای developer ها دوستانه بود و compiler زبان جدید C را نیز ارائه می‌ کرد. آسان کردن نوشتن program ها و به‌اشتراک‌ گذاری آن‌ ها برای programmer ها ، UNIX را به‌ شدت محبوب کرد. احتمالاً این محبوبیت تا حد زیادی به این دلیل نیز بود که نویسندگان آن ، نسخه‌ های سیستم را به‌ صورت رایگان در اختیار هر کسی که می‌ خواست قرار می‌ دادند. رویکردی که شکلی اولیه از open-source software به شمار می‌ رفت. 

یکی دیگر از عوامل حیاتی در اهمیت UNIX ، دسترس‌پذیری و خوانایی کد آن بود. وجود یک kernel کوچک و زیبا که به زبان C نوشته شده بود ، دیگران را تشویق می‌ کرد تا با kernel کار کنند و ویژگی‌ های جدید و جذابی به آن بیفزایند. برای مثال، گروهی ماهر در Berkeley به رهبری Bill Joy، یک distribution فوق‌العاده به نام Berkeley Systems Distribution (BSD) ساختند که زیرسیستم‌ های پیشرفته‌ ای برای virtual memory و file system و networking داشت. Joy بعد ها شرکت Sun Microsystems را به‌ همراه دیگران تأسیس کرد.

متأسفانه ، گسترش UNIX تا حدی کند شد زیرا شرکت‌ ها تلاش کردند مالکیت آن را در اختیار بگیرند و از آن سود کسب کنند. این نتیجه‌ ای ناخوشایند ، اما رایج از دخالت وکلا بود. بسیاری از شرکت‌ ها نسخه‌ های مخصوص خودشان را داشتند مثلاً SunOS از  Sun Microsystems یا AIX از IBM و HPUX که به آن «H-Pucks» هم می‌ گویند از HP و IRIX از SGI. کشمکش‌ های حقوقی میان AT&T/Bell Labs و سایر بازیگران این حوزه ، سایه‌ای تیره بر UNIX انداخت و بسیاری را به این فکر واداشت که آیا این سیستم زنده خواهد ماند یا نه ، به‌ ویژه زمانی که Windows معرفی شد و بخش بزرگی از بازار PC را در اختیار گرفت.

#### ASIDE: AND THEN CAME LINUX

خوشبختانه برای UNIX ، یک هکر جوان فنلاندی به اسم Linus Torvalds تصمیم گرفت نسخه خودش از UNIX را بنویسد. سیستمی که شدیداً از اصول و ایده‌ های سیستم اصلی الهام گرفته بود ، ولی از code base خود UNIX استفاده نمی‌ کرد و به این شکل ، از دردسرهای حقوقی هم دور می‌ ماند. او از آدم‌ های مختلفی از سراسر دنیا کمک گرفت و کم‌ کم Linux به وجود آمد و در کنار آن ، جنبش مدرن open-source software هم شکل گرفت. با شروع عصر internet ، بیشتر شرکت‌ها ، مثل Google ، Amazon ، Facebook تصمیم گرفتن از Linux استفاده کنند ، چون رایگان بود و خیلی راحت می‌ شد آن را مطابق نیازهای خودشان تغییر بدهند. در واقع ، تصور موفقیت این شرکت‌ های جدید بدون وجود چنین سیستمی خیلی سخت بود. وقتی smartphone ها تبدیل شدن به پلتفرم غالبی که کاربران با آن سر و کار داشتن ، Linux آنجا هم از طریق Android به دلایل مختلف توانست جایگاه خودش رو پیدا و تثبیت کند. Steve Jobs هم سیستم NeXTStep خودش را که مبتنی بر UNIX بود ، با خودش به Apple آورد و به این ترتیب ، UNIX روی desktop ها هم محبوب شد هرچند خیلی از کاربران فناوری‌ های Apple احتمالاً حتی از این موضوع خبر ندارند و به این شکل UNIX همچنان باقی می‌ ماند حتی مهم‌ تر از هر زمان دیگری.

### 2.7 Summary

به این ترتیب، مقدمه‌ای بر OS داشتیم. operating system های امروزی استفاده از سیستم‌ ها را نسبتاً آسان می‌ کنند و تقریباً تمام operating system هایی که امروز به کار می‌ برید ، از تحولاتی که در سراسر این کتاب بررسی خواهیم کرد تأثیر گرفته‌ اند. متأسفانه به‌ دلیل محدودیت زمان بخش‌هایی از OS وجود دارند که در این کتاب به آن‌ ها نمی‌پردازیم برای مثال، مقدار زیادی کد networking در operating system ها وجود دارد که یادگیری بیشتر درباره آن را به خودتان واگذار می‌ کنیم تا با گذراندن درس networking دانش خود را در این زمینه گسترش دهید. به همین ترتیب ، graphics device ها نیز اهمیت ویژه‌ ای دارند و برای افزایش دانش خود در این زمینه ، می‌ توانید درس graphics را بگذرانید و در نهایت ، برخی کتاب‌ های operating system به‌ طور گسترده درباره security صحبت می‌ کنند. ما نیز تا حدی به این موضوع می‌پردازیم ، به این معنا که OS باید protection میان program های در حال اجرا را فراهم کند و به کاربران امکان دهد از file های خود محافظت کنند. اما به مسائل عمیق‌تر security که ممکن است در درس security با آن‌ ها آشنا شوید ، نمی‌پردازیم. 

با این حال، موضوعات مهم بسیاری را بررسی خواهیم کرد : از جمله مبانی virtualization مربوط به CPU و memory و مفهوم concurrency و persistence از طریق device ها و file system ها. نگران نباشید ، با اینکه مسیر طولانی‌ ای در پیش داریم ، بخش عمده آن بسیار جالب خواهد بود و در پایان این مسیر، درک تازه‌ ای از نحوه عملکرد واقعی سیستم‌ های computer به دست خواهید آورد.
