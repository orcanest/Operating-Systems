## 💻 مقدمه ای بر سیستم عامل
### 📙 ترجمه کتاب Operating Systems: Three Easy Pieces (OSTEP) 

وقتی یک program اجرا می‌ شود چه اتفاقی می‌ افتد ؟ یک program در حال اجرا فقط یک کار بسیار ساده انجام می‌ دهد اینکه instruction اجرا می‌ کند. میلیون‌ ها بار و امروزه حتی میلیارد ها بار در هر ثانیه ، processor یک instruction را از memory میاد fetch می‌ کند ، آن را decode می‌ کند یعنی تشخیص می‌ دهد این کدام instruction است و آن را execute می‌ کند یعنی کاری را انجام می‌ دهد که قرار است انجام شود ، مثل جمع دو عدد ، دسترسی به memory ، بررسی یک شرط ، jump به یک function و مانند آن . پس از اتمام این instruction هم processor به سراغ instruction بعدی می‌ رود و همین‌ طور ادامه می‌ دهد ، تا سرانجام program تمام شود.

بدین ترتیب ، اصول اولیه مدل Von Neumann در محاسبات را توصیف کردیم. ساده به نظر می‌ رسد ، درست است؟ اما در این درس خواهیم آموخت که در حین اجرای یک program ، کارهای عجیب و پیچیده بسیار دیگری هم در پس‌ زمینه در جریان است که هدف اصلی‌ شان آسان‌ تر کردن استفاده از سیستم است. در واقع مجموعه‌ ای از software وجود دارد که مسئول آسان کردن اجرای program هاست ( حتی این امکان را می‌ دهد که به‌ ظاهر چندین program را هم‌ زمان اجرا کنید) ، به program ها اجازه می‌ دهد memory را به اشتراک بگذارند ، و آن‌ ها را قادر می‌ سازد با devices تعامل کنند ، و کارهای جالب دیگری از این دست. این مجموعه از software را **operating system (OS)** می‌ نامند ، چون مسئول این است که سیستم به‌ صورت صحیح و کارآمد و به شکلی آسان برای استفاده operate کند.

روش اصلی که OS این کار را انجام می‌ دهد، تکنیکی عمومی است که آن را **virtualization** می‌ نامیم. یعنی OS یک physical resource (مثل processor یا memory یا disk) را می‌ گیرد و آن را به شکل virtual  قدرتمند تر و آسان‌ تر برای استفاده از همان resource تبدیل می‌ کند. به همین دلیل گاهی operating system را یک **virtual machine** هم می‌ نامیم. البته برای اینکه کاربران بتوانند به OS بگویند چه کاری انجام دهد و از قابلیت‌ های virtual machine استفاده کنند (مثل اجرای یک program ، تخصیص memory یا دسترسی به یک file)، OS همچنین چند interface (یعنی API) فراهم می‌ کند که می‌ توانید آن‌ ها را فراخوانی کنید. یک OS معمولی در واقع چند صد **system call** را در اختیار application ها قرار می‌ دهد یا  به اصطلاح **export** می‌کند. چون OS این call ها را برای اجرای program ها ، دسترسی به memory و devices و کارهای مرتبط دیگر فراهم می‌ کند ، گاهی هم می‌گوییم OS یک **standard library** به application ها ارائه می‌ دهد.

در نهایت ، چون virtualization اجازه می‌ دهد بسیاری از program ها اجرا شوند و در نتیجه CPU را به اشتراک بگذارند ، بسیاری از program ها هم‌ زمان به instruction ها و داده خودشان دسترسی داشته باشند و در نتیجه memory را به اشتراک بگذارند و بسیاری از program ها به devices دسترسی پیدا کنند و در نتیجه disk و غیره را به اشتراک بگذارند . OS گاهی با عنوان ** resource manager** شناخته می‌ شود. هر یک از CPU و memory و disk یک resource از سیستم است. پس نقش operating system این است که آن resource ها را مدیریت کند ، چه به‌ صورت کارآمد ، چه منصفانه یا با بسیاری اهداف ممکن دیگر. برای درک بهتر نقش OS، چند مثال را بررسی می‌ کنیم.

### 2.1 Virtualizing the CPU

برنامه زیر نخستین program ما را نشان می‌ دهد ، کار زیادی انجام نمی‌ دهد. در واقع فقط()Spin را فراخوانی می‌ کند. function‌ که مدام زمان را بررسی می‌ کند و وقتی یک ثانیه از اجرایش گذشت برمی‌ گردد. سپس string را که user در command line داده چاپ می‌ کند و این کار را تا ابد تکرار می‌ کند.

```c

#include <stdio.h>
#include <stdlib.h>
#include <sys/time.h>
#include <assert.h>
#include "common.h"

int
main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "usage: cpu <string>\n");
        exit(1);
    }
    char *str = argv[1];
    while (1) {
        Spin(1);
        printf("%s\n", str);
    }
    return 0;
}

```

فرض کنید این file را با نام cpu.c ذخیره می‌ کنیم و تصمیم می‌ گیریم آن را روی سیستمی با یک processor (یا CPU ، که گاهی این‌ گونه می‌ نامیم) compile و اجرا کنیم. آنچه می‌ بینیم این است :

```
prompt> gcc -o cpu cpu.c -Wall
prompt> ./cpu "A"
A
A
A
A
^C
prompt>
```

اجرای چندان جالبی نیست. سیستم program را شروع می‌ کند ، program مدام زمان را بررسی می‌ کند تا یک ثانیه بگذرد. وقتی یک ثانیه گذشت ، کد string ورودی user که در این مثال حرف «A» را چاپ می‌ کند و ادامه می‌ دهد. توجه کنید که program تا ابد اجرا می‌ شود. فقط با فشردن «ctrl+c» که در سیستم‌ های مبتنی بر UNIX هم program را که در foreground در حال اجراست terminate می‌ کند ، می‌توانیم آن را متوقف کنیم.

حالا همین کار را انجام می‌ دهیم ، اما این بار چندین instance مختلف از همین program را اجرا می‌ کنیم. شکل زیر نتایج این مثال کمی پیچیده‌ تر را نشان می‌ دهد.


خب ، حالا کار جالب‌ تر شد. با اینکه فقط یک processor داریم ، به‌ نوعی هر چهار program به نظر می‌ رسد هم‌ زمان در حال اجرا هستند! این کار چگونه رخ می‌ دهد؟

> توجه کنید که با استفاده از نماد & چهار process را هم‌ زمان اجرا کردیم. این کار در shell از نوع tcsh یک job را در background اجرا می‌ کند ، یعنی کاربر می‌ تواند بلافاصله دستور بعدی‌ اش را وارد کند ، که در این مورد اجرای program دیگری است. semi-colon بین دستورها در tcsh امکان اجرای چند program را به‌ صورت هم‌ زمان می‌ دهد. اگر از shell دیگری مثلاً bash استفاده می‌ کنید ، کمی متفاوت کار می‌ کند.

معلوم می‌ شود که operating system ، با کمک hardware ، مسئول ایجاد این توهم است. یعنی توهم اینکه سیستم تعداد بسیار زیادی CPU مجازی (virtual CPU) دارد. تبدیل یک CPU (یا مجموعه‌ ای کوچک از آن‌ ها) به تعداد به‌ ظاهر بی‌ نهایتی CPU که در نتیجه امکان اجرای به‌ ظاهر هم‌ زمان بسیاری از program هاست ، همان چیزی است که virtualizing the CPU می‌ نامیم که تمرکز اولین بخش اصلی این کتاب است.

البته برای اجرا کردن program ها ، متوقف کردن‌ شان و به‌ طور کلی گفتن اینکه OS کدام program ها را اجرا کند ، باید interface‌ هایی ( API هایی ) وجود داشته باشد که بتوانید با آن‌ ها خواسته‌ هایتان را به OS اعلام کنید. در سراسر این کتاب درباره این API ها صحبت خواهیم کرد. در واقع این‌ ها راه اصلی تعامل بیشتر کاربران با operating system ها هستند. ممکن است متوجه شده باشید که توانایی اجرای چند program به‌ صورت هم‌ زمان انواع پرسش‌های جدید را پیش می‌ آورد. مثلاً اگر دو program بخواهند در یک زمان مشخص اجرا شوند ، کدام باید اجرا شود؟ پاسخ این پرسش را یک **policy** از OS می‌ دهد. policy ها در جاهای مختلف زیادی از یک OS برای پاسخ به این نوع پرسش‌ ها به کار می‌ روند ، ما هنگام یادگیری mechanism های پایه‌ ای که operating system ها پیاده‌ سازی می‌کنند مثل توانایی اجرای چند program به‌ صورت هم‌ زمان آن‌ها را هم مطالعه خواهیم کرد. از این‌ رو است که OS نقش resource manager را دارد.

### 2.2 Virtualizing Memory

حالا به memory می‌ پردازیم. مدل physical memory که ماشین‌ های مدرن ارائه می‌ دهند بسیار ساده است. Memory فقط یک آرایه از bytes است ، برای خواندن از memory باید یک address مشخص کرد تا بتوان به داده ذخیره‌ شده در آن دسترسی یافت و برای write یا update در memory باید علاوه بر آن ، داده مورد نظر برای write در address داده‌ شده را هم مشخص کرد.

در طول اجرای یک program ، به memory دائماً دسترسی صورت می‌ گیرد. یک program همه data structure هایش را در memory نگه می‌ دارد و از طریق instruction های مختلفی مثل load ها و store ها ، یا دیگر instruction های صریحی که برای انجام کارشان به memory دسترسی دارند ، به آن‌ ها دسترسی پیدا می‌ کند. فراموش نکنید که خودِ هر instruction از program هم در memory است بنابراین در هر instruction fetch هم به memory دسترسی صورت می‌گیرد.

بیایید به program زیر نگاه کنیم که با فراخوانی()malloc مقداری memory تخصیص می‌ دهد :

```c
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
#include "common.h"

int
main(int argc, char *argv[])
{
    int *p = malloc(sizeof(int));             // a1
    assert(p != NULL);
    printf("(%d) address of p: %08x\n",
           getpid(), (unsigned) p);           // a2
    *p = 0;                                   // a3
    while (1) {
        Spin(1);
        *p = *p + 1;
        printf("(%d) p: %d\n", getpid(), *p); // a4
    }
    return 0;
}
```

خروجی این program را این‌ جا می‌ توانید ببینید :

```
prompt> ./mem
(2134) memory address of p: 00200000
(2134) p: 1
(2134) p: 2
(2134) p: 3
(2134) p: 4
(2134) p: 5
^C
```

این program چند کار انجام می‌ دهد. اول ، مقداری memory تخصیص می‌ دهد (خط a1). سپس address آن memory را چاپ می‌ کند (a2) بعد عدد صفر را در اولین slot از memory تازه‌ تخصیص‌ یافته قرار می‌ دهد (a3). در نهایت وارد یک حلقه می‌ شود، یک ثانیه تأخیر می‌ دهد و مقدار ذخیره‌ شده در address را که p نگه داشته یک واحد افزایش می‌ دهد. با هر دستور print ، چیزی به نام process identifier (یا همان PID) برنامه در حال اجرا را هم چاپ می‌ کند. این PID برای هر process در حال اجرا یکتاست.

باز هم، این نتیجه اول چندان جالب نیست. memory تازه‌ تخصیص‌ یافته در address ‏00200000 است. با اجرای  program ، مقدار به‌ آهستگی به‌ روز می‌ شود و نتیجه چاپ می‌ گردد. حالا دوباره چندین instance از همین program را اجرا می‌ کنیم تا ببینیم چه می‌ شود :

```
prompt> ./mem &; ./mem &
[1] 24113
[2] 24114
(24113) memory address of p: 00200000
(24114) memory address of p: 00200000
(24113) p: 1
(24114) p: 1
(24114) p: 2
(24113) p: 2
(24113) p: 3
(24114) p: 3
(24113) p: 4
(24114) p: 4
...
```

از این مثال می‌ بینیم که هر program در حال اجرا ، memory را در همان address یعنی 00200000 تخصیص داده است و به نظر می‌ رسد هر کدام مقدار موجود در 00200000 را مستقل از دیگری به‌ روز می‌ کند. به طوری که هر program در حال اجرا memory خصوصی خودش را دارد ، به‌ جای اینکه همان physical memory را با دیگر program های در حال اجرا به اشتراک بگذارد.

در واقع دقیقاً همین اتفاق این‌ جا می‌ افتد ، چون OS در حال virtualizing memory است. هر process به virtual address space خصوصی خودش (که گاهی فقط address space نامیده می‌ شود) دسترسی دارد ، و OS به‌ نوعی آن را روی physical memory ماشین map می‌ کند. یک memory reference درون یک program در حال اجرا بر address space دیگر process ها (یا خودِ OS) تأثیر نمی‌ گذارد. از دید program در حال اجرا ، گویی کل physical memory فقط برای خودش است. اما واقعیت این است که physical memory یک resource مشترک است که توسط operating system مدیریت می‌ شود. اینکه دقیقاً چگونه همه این‌ ها انجام می‌ شود نیز موضوع بخش اول این کتاب یعنی virtualization است.

### 2.3 Concurrency

یکی دیگر از موضوعات اصلی این کتاب **concurrency** است. ما از این اصطلاح مفهومی برای اشاره به مجموعه‌ ای از مسائل استفاده می‌ کنیم که هنگام کار روی چندین کار به‌ صورت هم‌ زمان concurrently در یک program پیش می‌ آید و باید حل شوند. مسائل concurrency ابتدا در خودِ operating system پدید آمدند. همان‌ طور که در مثال‌ های virtualization بالا دیدید ، OS چندین کار را هم‌ زمان مدیریت می‌ کند ، ابتدا یک process را اجرا می‌ کند ، بعد process دیگری را و همین‌ طور ادامه می‌ دهد ، معلوم می‌ شود که انجام این کار به مسائل عمیق و جالبی می‌ انجامد. متأسفانه مسائل concurrency دیگر فقط به خودِ OS محدود نیستند. در واقع program های multi-threaded مدرن هم همین مسائل را نشان می‌ دهند. بیایید این را با مثالی از یک program (multi-threaded) نشان دهیم :

```c
#include <stdio.h>
#include <stdlib.h>
#include "common.h"

volatile int counter = 0;
int loops;

void *worker(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        counter++;
    }
    return NULL;
}

int
main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "usage: threads <value>\n");
        exit(1);
    }
    loops = atoi(argv[1]);
    pthread_t p1, p2;
    printf("Initial value : %d\n", counter);

    Pthread_create(&p1, NULL, worker, NULL);
    Pthread_create(&p2, NULL, worker, NULL);
    Pthread_join(p1, NULL);
    Pthread_join(p2, NULL);
    printf("Final value   : %d\n", counter);
    return 0;
}
```

ممکن است فعلاً این مثال را کامل نفهمید و در فصل‌ های بعدی ، در بخش concurrency کتاب ، درباره آن بسیار بیشتر خواهیم آموخت، اما ایده اصلی ساده است. program اصلی با استفاده از()Pthread_create دو thread ایجاد می‌ کند. می‌ توانید یک thread را function‌ در نظر بگیرید که در همان memory space سایر function ها اجرا می‌ شود ، و بیش از یکی از آن‌ ها هم‌ زمان فعال‌ اند. در این مثال ، هر thread اجرای خود را از روتینی به نام()worker شروع می‌ کند ، که در آن فقط یک counter را در یک حلقه به تعداد loops بار افزایش می‌ دهد.

در ادامه رونوشتی از اتفاقی است که با اجرای این program و مقداردهی متغیر loops به 1000 رخ می‌ دهد. مقدار loops تعیین می‌ کند که هر یک از دو worker چند بار counter مشترک را در یک حلقه افزایش دهد. وقتی program با loops برابر 1000 اجرا می‌ شود ، انتظار دارید مقدار نهایی counter چه باشد ؟

```
prompt> gcc -o thread thread.c -Wall -pthread
prompt> ./thread 1000
Initial value : 0
Final value   : 2000
```

همان‌طور که احتمالاً حدس زدید وقتی هر دو thread تمام می‌ شوند ، مقدار نهایی counter برابر 2000 است، چون هر thread مقدار counter را 1000 بار افزایش داده است. در واقع وقتی مقدار ورودی loops برابر N باشد ، انتظار داریم خروجی نهایی program برابر 2N باشد اما معلوم می‌ شود زندگی به این سادگی نیست. بیایید همین program را با مقادیر بزرگ‌ تر برای loops اجرا کنیم و ببینیم چه می‌ شود:

```
prompt> ./thread 100000
Initial value : 0
Final value   : 143012      // huh??
prompt> ./thread 100000
Initial value : 0
Final value   : 137298      // what the??
```

در این اجرا ، وقتی مقدار ورودی را 100,000 دادیم ، به‌ جای اینکه مقدار نهایی 200,000 شود ابتدا 143,012 گرفتیم. بعد وقتی program را بار دوم اجرا کردیم ، نه‌ تنها دوباره مقدار اشتباه گرفتیم بلکه مقداری متفاوت از دفعه قبل هم به دست آمد. در واقع اگر program را با مقادیر بزرگ loops بارها و بارها اجرا کنید ، ممکن است گاهی حتی جواب درست هم بگیرید ، پس چرا این اتفاق می‌ افتد ؟

معلوم می‌ شود دلیل این نتایج عجیب و غیرمعمول به نحوه اجرای instruction ها مربوط می‌ شود ، که یکی‌ یکی اجرا می‌ شوند. متأسفانه بخش کلیدی program بالا یعنی جایی که counter مشترک افزایش می‌ یابد ، سه instruction می خواهد :

- یکی برای load کردن مقدار counter از memory به یک register.
- یکی برای افزایش آن.
- یکی برای store کردن آن به memory. 

چون این سه instruction به‌صورت atomic یعنی همگی یکجا اجرا نمی‌ شوند ، اتفاقات عجیبی ممکن است رخ دهد. همین مسئله concurrency است که در بخش دوم کتاب با جزئیات بسیار به آن می‌پردازیم.

### 2.4 Persistence

سومین موضوع اصلی درس ، **persistence** است. در system memory ، داده به‌ راحتی از دست می‌ رود، چون devices مثل DRAM مقادیر را به‌ صورت volatile ذخیره می‌ کنند. وقتی برق قطع شود یا سیستم crash کند ، هر داده موجود در memory از بین می‌ رود. بنابراین به hardware و software‌ نیاز داریم که بتواند داده را به‌ صورت persistent ذخیره کند. چنین ذخیره‌ سازی برای هر سیستمی حیاتی است، چون کاربران به داده‌ هایشان اهمیت زیادی می‌ دهند. hardware به شکل نوعی device از جنس input/output یا I/O است. در سیستم‌ های مدرن ، hard drive مخزن رایج اطلاعات بلند مدت است ، هرچند solid-state drive (SSD) ها هم در این حوزه در حال پیشرفت‌ اند. software‌ که در operating system که معمولاً disk را مدیریت می‌ کند file system نام دارد. پس مسئولیت ذخیره هر file که کاربر ایجاد می‌ کند ، به شکلی قابل‌ اعتماد و کارآمد ، روی disk های سیستم با اوست.

برخلاف abstraction هایی که OS برای CPU و memory فراهم می‌ کند ، OS برای هر application یک disk خصوصی و virtualized نمی‌ سازد. در عوض فرض می‌ شود که اغلب کاربران می‌ خواهند اطلاعات موجود در file ها را به اشتراک بگذارند. مثلاً هنگام نوشتن یک برنامه C ، ممکن است ابتدا از یک editor مثلاً Emacs برای ایجاد و ویرایش file زبان C استفاده کنید (emacs -nw main.c). وقتی کارتان تمام شد ، ممکن است از compiler برای تبدیل source code به یک executable استفاده کنید (مثلاً gcc -o main main.c) و وقتی همه‌ چیز تمام شد ، ممکن است executable جدید را اجرا کنید (مثلاً main/.) ، بنابراین می‌ بینید که file ها چگونه میان process های مختلف به اشتراک گذاشته می‌ شوند. Emacs اول file ایجاد می‌ کند که به‌ عنوان ورودی compiler به کار می رود و compiler از آن file ورودی برای ایجاد یک file اجرایی جدید استفاده می‌ کند و در نهایت executable جدید اجرا می‌ شود و به این ترتیب یک program جدید متولد می‌ شود. برای درک بهتر این موضوع ، بیایید به مقداری کد نگاه کنیم. کد زیر نشان می‌ دهد که فایلی (tmp/file/) می‌ سازد که حاوی «string «hello world است.

```c
#include <stdio.h>
#include <unistd.h>
#include <assert.h>
#include <fcntl.h>
#include <sys/types.h>

int
main(int argc, char *argv[])
{
    int fd = open("/tmp/file", O_WRONLY | O_CREAT | O_TRUNC, S_IRWXU);
    assert(fd > -1);
    int rc = write(fd, "hello world\n", 13);
    assert(rc == 13);
    close(fd);
    return 0;
}
```

برای انجام این کار، program سه فراخوانی به operating system انجام می‌ دهد. اولی یعنی()open، فایل را باز و ایجاد ش می‌ کند.  دومی()write، مقداری داده در file می‌ نویسد و سومی()close صرفاً file را می‌ بندد و بدین ترتیب نشان می‌ دهد که program دیگر داده بیشتری در آن نخواهد نوشت. این system call ها به بخشی از operating system به نام file system هدایت می‌ شوند ، که سپس درخواست‌ ها را پردازش می‌ کند و نوعی error code به کاربر برمی‌ گرداند.

ممکن است کنجکاو باشید OS برای نوشتن واقعی روی disk چه می‌ کند. ما نشانتان می‌ دهیم ، اما باید قول بدهید ابتدا چشمانتان را ببندید چون خیلی ناخوشایند است. file system باید کار نسبتاً زیادی انجام دهد : اول باید تعیین کند این داده جدید کجای disk قرار بگیرد و بعد آن را در ساختارهای مختلفی که file system نگه می‌ دارد پیگیری کند. انجام این کار مستلزم صدور I/O request ها به storage device زیرین است ، چه برای خواندن ساختارهای موجود و چه برای به‌ روزرسانی آن‌ ها. هر کسی که device driver نوشته باشد می‌ داند که وادار کردن یک device به انجام کاری به نمایندگی از شما ، فرایندی پیچیده و پر جزئیات است. این کار نیازمند دانش عمیق از low-level device interface و semantics دقیق آن است. خوشبختانه OS از طریق system call هایش راهی استاندارد و ساده برای دسترسی به devices فراهم می‌ کند. بنابراین OS گاهی به‌ عنوان یک standard library دیده می‌ شود.

البته جزئیات بسیار بیشتری درباره نحوه دسترسی به devices و اینکه file system ها چگونه داده را به‌ صورت persistent روی devices مذکور مدیریت می‌ کنند وجود دارد. به دلایل مربوط به performance ، بیشتر file system ها ابتدا این نوشتن‌ ها را مدتی به تأخیر می‌ اندازند ، به این امید که آن‌ ها را در گروه‌ های بزرگ‌ تر batch کنند. برای رسیدگی به مشکل crash شدن سیستم در حین نوشتن ، بیشتر file system ها نوعی write protocol پیچیده ، مثل journaling یا copy-on-write ، را در خود جای می‌ دهند و نوشتن‌ ها روی disk را با دقت مرتب می‌ کنند تا اگر در میانه توالی نوشتن خرابی رخ داد ، سیستم بتواند پس از آن به وضعیتی معقول بازیابی شود. برای کارآمد کردن عملیات رایج مختلف ، file system ها data structure ها و access method های متنوعی به کار می‌ گیرند ، از list‌ های ساده تا b-tree های پیچیده. اگر هنوز این‌ ها برایتان معنا ندارد، عالی است! در بخش سوم این کتاب ، درباره persistence ، بسیار بیشتر درباره همه این موارد صحبت خواهیم کرد. آن‌ جا ابتدا درباره devices و I/O به‌ طور کلی بحث می‌ کنیم و سپس درباره disk ها ، RAID ها و file system ها با جزئیات فراوان.

### 2.5 Design Goals

حالا تا حدی می‌ دانید یک OS واقعاً چه می‌کند : physical resource هایی مثل CPU یا memory یا disk را می‌ گیرد و آن‌ ها را virtualize می‌ کند. با مسائل دشوار و ظریف مربوط به concurrency دست‌ و پنجه نرم می‌ کند. و file ها را به‌ صورت persistent ذخیره می‌ کند و در نتیجه آن‌ ها را در بلند مدت ایمن نگه می‌ دارد. با توجه به اینکه می‌ خواهیم چنین سیستمی بسازیم ، باید اهدافی در ذهن داشته باشیم که به متمرکز شدن طراحی و پیاده‌ سازی کمک کنند و در صورت لزوم trade-off برقرار کنیم. یافتن مجموعه درست trade-off ها کلید ساخت سیستم‌ هاست.

یکی از اساسی‌ ترین اهداف ، ساختن مجموعه‌ ای از abstraction ها برای راحت و آسان کردن استفاده از سیستم است. abstraction ها در هر کاری که در computer science انجام می‌ دهیم اساسی هستند. abstraction این امکان را می‌ دهد که یک program بزرگ را با تقسیم‌ کردن آن به قطعات کوچک و قابل‌ فهم بنویسیم. چنین program که در یک زبان سطح‌ بالا مثل C بنویسیم بدون اینکه به assembly فکر کنیم. کد را به assembly بنویسیم بدون اینکه به logic gate ها فکر کنیم و یک processor را از gate ها بسازیم بدون اینکه زیاد به transistor ها فکر کنیم. abstraction آن‌قدر اساسی است که گاهی اهمیتش را فراموش می‌ کنیم ، اما ما این‌ جا فراموشش نخواهیم کرد بنابراین در هر بخش، درباره برخی abstraction های مهمی که در طول زمان شکل گرفته‌ اند بحث می‌ کنیم تا راهی برای فکر کردن درباره اجزای OS در اختیارتان بگذاریم.

یکی از اهداف در طراحی و پیاده‌ سازی یک operating system فراهم کردن high performance است. به عبارت دیگر، هدف ما حداقل کردن overheads مربوط به OS است. virtualization و آسان کردن استفاده از سیستم ارزش زیادی دارند، اما نه به هر قیمتی. بنابراین باید تلاش کنیم virtualization و دیگر قابلیت‌ های OS را بدون overhead های بیش از حد فراهم کنیم. این overhead ها به اشکال مختلفی پدید می‌ آیند :  ** زمان اضافی instruction های بیشتر و فضای اضافی در memory یا روی disk**. ما به‌ دنبال راه‌ حل‌ هایی خواهیم بود که یکی از این دو یا هر دو را در صورت امکان هدف بگیرند کنند. با این حال کمال همیشه دست‌ یافتنی نیست ، چیزی که یاد می‌ گیریم متوجهش شویم و در جاهای مناسب تحملش کنیم.

هدف دیگر فراهم کردن **protection** میان application ها و همچنین میان OS و application هاست. چون می‌ خواهیم اجازه دهیم بسیاری از program ها هم‌ زمان اجرا شوند ، می‌ خواهیم مطمئن شویم رفتار بد مخرب یا تصادفی یکی از آن‌ ها به دیگران آسیب نمی‌زند و قطعاً نمی‌ خواهیم یک application بتواند به خودِ OS آسیب بزند چون این بر همه program های در حال اجرا روی سیستم تأثیر می‌ گذارد. protection در قلب یکی از اصول اصلی زیربنای یک operating system ، یعنی **isolation** قرار دارد. جداسازی process ها از یکدیگر کلید protection است و بنابراین زیربنای بخش بزرگی از کارهایی است که یک OS باید انجام دهد.

همچنین operating system باید بدون وقفه کار کند. وقتی fail شود همه application های در حال اجرا روی سیستم هم fail می‌ شوند. به‌ خاطر این وابستگی ، operating system ها اغلب تلاش می‌ کنند درجه بالایی از **reliability** فراهم کنند. با پیچیده‌ تر شدن روزافزون operating system ها که گاهی میلیون‌ها خط کد دارند ، ساختن یک operating system قابل‌اعتماد چالش بزرگی است و در واقع بخش زیادی از پژوهش‌ های جاری در این حوزه دقیقاً روی همین مسئله متمرکز است.

اهداف دیگری هم منطقی هستند مثلاً **energy-efficiency** مهم است. **security** که در واقع گسترشی از protection است در برابر application های مخرب حیاتی است ، به‌ ویژه در این زمانه ی بسیار شبکه‌ ای و **mobility** اهمیت فزاینده‌ ای دارد ، چون OS ها روی devices کوچک‌ تر و کوچک‌ تری اجرا می‌ شوند. بسته به نحوه استفاده از سیستم ، OS اهداف متفاوتی خواهد داشت و در نتیجه احتمالاً دست‌ کم کمی متفاوت پیاده‌ سازی می‌ شود. با این حال ، همان‌طور که خواهیم دید بسیاری از اصولی که درباره ساخت operating system ها ارائه می‌ کنیم در طیف گسترده‌ ای از devices مفیدند.

### 2.6 Some History

پیش از پایان دادن به این مقدمه ، تاریخچه کوتاهی از چگونگی توسعه operating system ها ارائه می‌ کنیم. مثل هر سیستمی که انسان‌ ها ساخته‌ اند ، ایده‌ های خوب در طول زمان در operating system ها انباشته شدند ، همان‌ طور که مهندسان یاد گرفتند چه چیزی در طراحی‌شان مهم است. این‌ جا چند تحول عمده را بررسی می‌ کنیم. برای بحثی غنی‌ تر، تاریخچه عالی Brinch Hansen دربارهٔ operating system ها را ببینید.

#### Early Operating Systems: Just Libraries

در ابتدا operating system کار چندانی نمی‌ کرد. اساساً فقط مجموعه‌ ای از library از function های پرکاربرد بود مثلاً به‌ جای اینکه هر programmer سیستم کد low-level برای مدیریت I/O را خودش بنویسد ، «OS» چنین API هایی را فراهم می‌ کرد و در نتیجه کار را برای developer آسان‌ تر می‌ کرد. معمولاً در آن سیستم‌ های قدیمی mainframe ، در هر زمان یک program اجرا می‌ شد که توسط یک operator انسانی کنترل می‌ شد. بسیاری از کارهایی که فکر می‌ کنید یک OS مدرن انجام می‌ دهد مثلاً تصمیم‌ گیری درباره ترتیب اجرای job ها توسط این operator انجام می‌ شد. اگر developer با هوشی بودید ، با این operator مهربان می‌ بودید تا شاید job شما را به ابتدای صف ببرد. این شیوه محاسبه با نام batch processing شناخته می‌ شد، چون تعدادی job آماده می‌ شد و سپس توسط operator به‌ صورت یک «batch» اجرا می‌ شد. computer ها تا آن زمان به‌ صورت interactive استفاده نمی‌ شدند ، به‌ خاطر هزینه صرفاً آن‌ قدر پرهزینه بود که کاربری پشت computer بنشیند و از آن استفاده کند ، چون بیشتر اوقات computer فقط idle می‌ ماند و برای آن مرکز، ساعتی صد ها هزار دلار هزینه داشت.

#### Beyond Libraries: Protection

در حرکت از یک library ساده از سرویس‌ های پرکاربرد به سمت چیزی بیشترoperating system ها نقش محوری‌ تری در مدیریت ماشین‌ ها بر عهده گرفتند. یک جنبه مهم این بود که فهمیدند کدی که از طرف OS اجرا می‌ شود ویژه است. کنترل devices را در دست دارد و بنابراین باید با آن متفاوت از کد application معمولی برخورد شود. چرا ؟ تصور کنید به هر application اجازه می‌ دادید از هر نقطه‌ای از disk بخواند و مفهوم privacy از بین می‌ رفت ، چون هر program می‌ توانست هر file را بخواند. بنابراین پیاده‌ سازی یک file system برای مدیریت file هایتان به‌ صورت یک library معنای چندانی ندارد به‌ جای آن ، چیز دیگری لازم بود.

بدین ترتیب ایده system call ابداع شد ، که پیشگام آن سیستم محاسباتی Atlas بود. به‌ جای اینکه روتین‌ های OS را به‌ صورت یک library عرضه کنند که برای دسترسی به آن‌ ها فقط یک procedure call انجام می‌ دهید، ایده این بود که یک جفت instruction ویژه hardware و hardware state اضافه شود تا گذار به درون OS به فرایندی رسمی‌ تر و کنترل‌ شده تبدیل شود.

تفاوت کلیدی میان system call و procedure call این است که system call کنترل را به درون OS منتقل می‌ کند و هم‌ زمان **hardware privilege level** را بالا می‌ برد. application های کاربر در چیزی اجرا می‌ شوند که user mode نامیده می‌ شود ، یعنی hardware آنچه application ها می‌ توانند انجام دهند را محدود می‌ کند مثلاً application که در user mode اجرا می‌ شود معمولاً نمی‌ تواند یک I/O request به disk آغاز کند ، به هر physical memory page دسترسی پیدا کند یا یک packet روی network بفرستد. وقتی یک system call آغاز می‌ شود معمولاً از طریق یک hardware instruction ویژه به نام trap ، hardware کنترل را به یک trap handler از پیش تعیین‌ شده که OS قبلاً تنظیم کرده است منتقل می‌ کند و هم‌ زمان privilege level را به kernel mode ارتقا می‌ دهد. در kernel mode هم OS دسترسی کامل به hardware سیستم دارد و در نتیجه می‌ تواند کارهایی مثل آغاز یک I/O request یا فراهم کردن memory بیشتر برای یک program را انجام دهد. وقتی OS رسیدگی به درخواست را تمام کرد ، کنترل را از طریق یک instruction ویژه به نام return-from-trap به کاربر برمی‌ گرداند ، که به user mode بازمی‌ گردد و هم‌ زمان کنترل را به همان جایی که application متوقف شده بود برمی‌ گرداند.

#### The Era of Multiprogramming

جایی که operating system ها واقعاً اوج گرفتند ، دوره فراتر از mainframe بود ، یعنی دوره minicomputer. ماشین‌ های کلاسیکی مثل خانواده PDP از شرکت Digital Equipment که computer ها را بسیار ارزان‌ تر کردند بنابراین به‌ جای داشتن یک mainframe برای هر سازمان بزرگ ، حالا مجموعه‌ ای کوچک‌ تر از افراد درون یک سازمان احتمالاً می‌ توانستند computer خودشان را داشته باشند. جای تعجب نیست که یکی از تأثیرات عمده این کاهش هزینه افزایش فعالیت developer ها بود. افراد باهوش بیشتری به computer ها دست یافتند و در نتیجه سیستم‌ های computer را وادار به انجام کارهای جالب‌ تر و زیباتری کردند.

به‌ طور خاص **multiprogramming** به‌ دلیل تمایل به استفاده بهتر از resource های ماشین رایج شد. به‌ جای اینکه فقط یک job در هر زمان اجرا شود ، OS تعدادی job را در memory بارگذاری می‌ کرد و سریعاً بین آن‌ ها switch می‌ کرد و بدین ترتیب CPU utilization را بهبود می‌ داد. این switch کردن به‌ ویژه مهم بود چون I/O device ها کند بودند. اینکه یک program روی CPU منتظر بماند تا I/O آن سرویس‌ دهی شود اتلاف زمان CPU بود. پس چرا به job دیگری switch نکنیم و آن را مدتی اجرا نکنیم ؟

تمایل به پشتیبانی از multiprogramming و overlap در حضور I/O و interrupt ها، توسعه مفهومی operating system ها را در جهت‌ های متعددی به نوآوری واداشت. مسائلی مثل **memory protection** مهم شدند. نمی‌خواهیم یک program بتواند به memory یک program دیگر دسترسی داشته باشد. فهم چگونگی مقابله با مسائل concurrency که multiprogramming معرفی کرد نیز حیاتی بود و اطمینان از اینکه OS با وجود interrupt ها درست رفتار می‌ کند چالش بزرگی است. این مسائل و موضوعات مرتبط را بعداً در کتاب مطالعه خواهیم کرد.

یکی از پیشرفت‌ های عملی بزرگ آن دوره معرفی operating system به نام **UNIX** بود ، عمدتاً به لطف Ken Thompson و Dennis Ritchie در Bell Labs همان شرکت تولید تلفن. UNIX ایده‌ های خوب زیادی را از operating system های مختلف گرفت ، اما آن‌ ها را ساده‌ تر و آسان‌ تر برای استفاده کرد. این تیم نوارهایی حاوی source code سیستم UNIX را برای افرادی در سراسر جهان می‌ فرستاد، که بسیاری از آن‌ ها سپس درگیر شدند و خودشان به سیستم افزودند.

#### The Modern Era

فراتر از minicomputer ، نوع جدیدی از ماشین آمد که ارزان‌ تر، سریع‌ ترو برای عموم مردم بود به نام personal computer یا همان PC که امروز می‌ نامیم. به رهبری ماشین‌های اولیه Apple مثلاً Apple II و IBM PC ، این نسل جدید ماشین‌ ها به‌ زودی به نیروی غالب در محاسبات تبدیل شدند ، چون هزینه پایین‌ شان امکان داشتن یک ماشین برای هر میز کار را فراهم می‌ کرد ، به‌جای یک minicomputer مشترک برای هر گروه کاری.

متأسفانه ، برای operating system ها ، PC در ابتدا گامی بزرگ به عقب بود ، چون سیستم‌ های اولیه درس‌ هایی را که در دوره minicomputer آموخته شده بود فراموش کردند یا هرگز از آن‌ها خبر نداشتند. مثلاً operating system های اولیه مانند DOS یعنی Disk Operating System از Microsoft فکر نمی‌ کردند memory protection مهم است. بنابراین یک application مخرب می‌توانست روی کل memory خط‌ خطی کند. نسل‌ های اول Mac OS نسخه 9 و قبل‌ تر رویکردی cooperative برای job scheduling اتخاذ کردند بنابراین یک thread که اتفاقی در یک infinite loop گیر می‌ کرد می‌ توانست کل سیستم را در اختیار بگیرد و reboot را اجباری کند. فهرست دردناک ویژگی‌ های OS که در این نسل از سیستم‌ ها وجود نداشت بلند است ، بسیار بلند تر از آنکه این‌ جا بتوان به‌ طور کامل بحث کرد.

خوشبختانه ، پس از چند سال رنج ، ویژگی‌ های قدیمی operating system های minicomputer راهشان را به desktop باز کردند. مثلاً Mac OS X در هسته خود UNIX دارد ، با تمام ویژگی‌ هایی که از چنین سیستم بالغی انتظار دارید. Windows نیز به‌ طور مشابه بسیاری از ایده‌ های عالی تاریخ computing را پذیرفته است ، به‌ ویژه با شروع از Windows NT ، جهشی بزرگ در فناوری OS مایکروسافت. حتی تلفن‌ های همراه امروزی operating system هایی مثل Linux اجرا می‌ کنند که بسیار بیشتر شبیه چیزی هستند که یک minicomputer در دهه ۱۹۷۰ اجرا می‌ کرد تا آنچه یک PC در دهه ۱۹۸۰ اجرا می‌ کرد. خوب است که می‌ بینیم ایده‌ های خوبی که در اوج دوران توسعه OS پدید آمدند راهشان را به دنیای مدرن پیدا کرده‌اند. حتی بهتر اینکه این ایده‌ ها همچنان در حال توسعه‌ اند و قابلیت‌ های بیشتری فراهم می‌ کنند و سیستم‌ های مدرن را برای کاربران و application ها حتی بهتر می‌ سازند.

#### ASIDE: THE IMPORTANCE OF UNIX

بیان اهمیت UNIX در تاریخ operating system ها دشوار است ، چون هر چه بگوییم کم است. UNIX که تحت تأثیر سیستم‌ های پیشین (به‌ ویژه سیستم مشهور Multics از MIT) بود ، ایده‌ های عالی بسیاری را گرد هم آورد و سیستمی ساخت که هم ساده بود و هم قدرتمند. زیربنای UNIX اصلی «Bell Labs» این اصل یکپارچه‌ کننده بود.ساختن program های کوچکِ قدرتمندی که بتوان آن‌ ها را به هم متصل کرد تا workflow های بزرگ‌ تری بسازند. shell ، جایی که دستورها را تایپ می‌ کنید ، primitive هایی مثل pipe ها را فراهم کرد تا چنین meta-level programming ممکن شود و بنابراین به‌ هم‌ زنجیر کردن program ها برای انجام کاری بزرگ‌ تر آسان شد. مثلاً برای یافتن خطوطی از یک text file که کلمه «foo» در آن‌ ها هست و سپس شمردن اینکه چند خط چنین است ، این را تایپ می‌کنید :

```grep foo file.txt|wc -l```

بدین ترتیب از program های grep و wc برای انجام کارتان استفاده می‌ کنید. محیط UNIX هم برای programmer ها و هم برای developer ها دوستانه بود و compiler زبان جدید C را هم ارائه می‌ کرد. آسان کردن نوشتن program ها و به‌ اشتراک‌ گذاری آن‌ ها برای programmer ها ، UNIX را بی‌ نهایت محبوب کرد و احتمالاً به این هم کمک زیادی کرد که نویسندگان نسخه‌ ها را به‌ رایگان به هر کسی که می‌ خواست می‌ دادند ، شکلی اولیه از open-source software.

از نظر اهمیت حیاتی ، دسترس‌ پذیری و خوانایی کد هم بود. داشتن یک kernel زیبا و کوچک که به زبان C نوشته شده بود دیگران را دعوت می‌کرد با kernel ور بروند و ویژگی‌ های جدید و جذاب بیفزایند. مثلاً گروهی کاربلد در Berkeley به رهبری Bill Joy ، یک distribution فوق‌العاده ساخت (Berkeley Systems Distribution یا BSD) که زیرسیستم‌ های پیشرفته‌ ای برای virtual memory و file system و networking داشت. Joy بعد ها Sun Microsystems را co-found کرد.

متأسفانه گسترش UNIX کمی کند شد ، چون شرکت‌ ها تلاش کردند مالکیت آن را مطالبه کنند و از آن سود ببرند ، نتیجه‌ ای ناخوشایند اما رایج از دخالت وکلا. بسیاری از شرکت‌ ها نسخه‌ های خودشان را داشتند : SunOS از Sun Microsystems و AIX از IBM و HPUX که به آن «H-Pucks» هم می‌ گویند از HP و IRIX از SGI. کشمکش‌ های حقوقی میان AT&T/Bell Labs  و این بازیگران دیگر ابری تیره بر UNIX افکند و بسیاری می‌ پرسیدند آیا زنده خواهد ماند ، به‌ ویژه وقتی Windows معرفی شد و بخش زیادی از بازار PC را در دست گرفت.

### 2.7 Summary

بدین ترتیب مقدمه‌ ای بر OS داشتیم. operating system های امروزی استفاده از سیستم‌ ها را نسبتاً آسان می‌ کنند و تقریباً همه operating system هایی که امروز استفاده می‌ کنید از تحولاتی که در سراسر کتاب بحث خواهیم کرد تأثیر گرفته‌اند. متأسفانه ، به‌ دلیل محدودیت زمان ، بخش‌هایی از OS هست که در کتاب پوشش نمی‌دهیم. مثلاً کد networking زیادی در operating system وجود دارد که یادگیری بیشتر درباره آن را به عهده خودتان می‌ گذاریم تا درس networking را بگذرانید. به‌ طور مشابه ، graphics devices اهمیت ویژه‌ای دارند که برای گسترش دانش‌ تان در آن جهت درس graphics را بگذرانید. در نهایت ، برخی کتاب‌ های operating system زیاد درباره security صحبت می کنند ، ما هم تا حدی درباره آن صحبت می‌کنیم ، به این معنا که OS باید protection میان program های در حال اجرا فراهم کند و به کاربران توانایی محافظت از file هایشان را بدهد ، اما به مسائل عمیق‌ تر security که ممکن است در درس security بیابید نمی‌ پردازیم. با این حال ، موضوعات مهم بسیاری هستند که پوشش خواهیم داد ، از جمله مبانی virtualization مربوط به CPU و memory و concurrency و persistence از طریق devices و file system ها. نگران نباشید با اینکه مسیر طولانی در پیش است ، بیشتر آن بسیار جالب است و در پایان راه درکی تازه از اینکه سیستم‌ های computer واقعاً چگونه کار می‌ کنند پیدا خواهید کرد.
